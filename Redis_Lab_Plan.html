1. Что делаем и зачем #

Цель лабы — не «потыкать redis-cli», а построить кусок реальной системы, где Redis закрывает четыре разные роли одновременно, и на своей шкуре почувствовать, где каждая роль подводит:

Роль RedisЧто решаетГде в проекте
Кэшснять нагрузку с PostgreSQL на горячих READкарточка товара — Cache-Aside
Хранилище сессийшарить сессии между несколькими PHP-воркерамиSESSION_DRIVER=redis
Примитив синхронизациине продать один и тот же товар дваждыdistributed lock на SET NX PX
Брокер событийасинхронная обработка заказа: email, аналитикаRedis Streams + consumer groups

Это осознанный выбор: Redis — не замена PostgreSQL и не замена RabbitMQ, а инструмент с своим набором компромиссов. Лаба специально ставит вас в ситуации, где эти компромиссы видны: что будет, если Redis перезапустится без AOF; что будет, если Pub/Sub-подписчик отвалился на секунду; что будет, если два процесса одновременно попробуют взять один и тот же лок.

ГЛАВНАЯ РАЗНИЦА С RABBITMQ

RabbitMQ — брокер, спроектированный вокруг доставки сообщений: маршрутизация, подтверждения, персистентность — всё из коробки. Redis — структура данных в памяти со скидкой на персистентность; очередь на нём вы строите сами из примитивов (Streams, List, ZSet). Это даёт гибкость и низкую задержку, но каждая гарантия, которую RabbitMQ даёт «бесплатно», в Redis — ваша ответственность и явный код.

2. Как Redis устроен внутри #

2.1. Однопоточность и event loop

Redis обрабатывает команды в одном потоке1 через event loop на основе epoll/kqueue. Это не узкое место, а осознанный выбор: убирает блокировки и гонки внутри самого Redis — каждая команда атомарна просто потому, что не может выполниться «наполовину» параллельно с другой. С Redis 6+ есть I/O-threads для чтения/записи сокетов, но сама логика команд по-прежнему однопоточна.

СЛЕДСТВИЕ

Любая «тяжёлая» команда — KEYS * на миллионе ключей, SORT без LIMIT, синхронный SAVE — блокирует вообще все остальные запросы на время своего выполнения. Отсюда правило лабы: KEYS запрещён в коде, только SCAN.

2.2. Структуры данных, которые мы используем

ТипКоманды в лабеЗачем нам
StringSET, GET, SETEX, SET...NX PXкэш карточки товара, distributed lock
HashHSET, HGETALL, HINCRBYсчётчик попыток retry по сообщению

2.3. Персистентность: RDB и AOF

Redis по умолчанию — база в памяти. Персистентность2 — это страховка, а не гарантия ACID:

  • RDB — периодический снапшот всей базы на диск (SAVE/BGSAVE). Компактно, быстро для рестарта, но теряет всё с момента последнего снапшота.
  • AOF (Append Only File) — журнал всех команд записи. С appendfsync everysec теряете максимум секунду данных при падении процесса; с always — почти ничего, но каждая запись ждёт fsync.

Для Streams это критично: если AOF выключен и Redis упал между XADD и следующим RDB-снапшотом — событие заказа потеряно безвозвратно, и PostgreSQL про него уже знает (запись есть), а Redis — нет. В лабе мы сознательно включаем AOF и разбираем на практике (шаг 1.2), что именно это меняет.

🔬 Под капотом: почему Redis — не замена персистентной очереди «из коробки»

Даже с appendfsync always у Redis нет publisher confirm в смысле RabbitMQ: клиент получает ответ на XADD сразу после записи в память, а fsync на диск может случиться позже (или не случиться, если процесс убит через kill -9 до записи в ОС-буфер). Это осознанный trade-off Redis: скорость важнее строгой durability по умолчанию. Именно поэтому в паре с Redis Streams почти всегда держат идемпотентный consumer и внешний источник истины (в нашем случае — PostgreSQL), а не полагаются на Streams как на единственную копию события.

2.4. Ключи, TTL и вытеснение (eviction)

У любого ключа может быть TTL3 (EXPIRE/PEXPIRE, или сразу в SET ... EX). Когда память заканчивается, поведение зависит от maxmemory-policy: noeviction (по умолчанию — команды записи начинают падать с ошибкой), allkeys-lru, volatile-lru и другие. Для кэша карточек товара мы используем volatile-lru — вытесняются только ключи с TTL, «вечные» структуры (Streams, счётчики) не трогаются.

2.5. Атомарность одной команды vs атомарность операции

Каждая отдельная команда Redis атомарна. Но «прочитать остаток товара, проверить > 0, списать» — это три обращения, и между ними может влезть другой клиент. Redis даёт три инструмента для настоящей атомарности составной операции: MULTI/EXEC (транзакция без промежуточных проверок условий), Lua-скрипты (выполняются атомарно, можно ветвиться) и SET NX как строительный блок для локов. В лабе резервирование стока делает Lua-скрипт (шаг 2.1) — это самый честный способ.

5. Паттерны: кэш, локи, rate limit, сессии #

5.1. Cache-Aside

Читаем: сначала GET product:{id}; промах (cache miss) — идём в PostgreSQL, кладём результат в Redis с TTL, отдаём. Пишем: обновили товар в PostgreSQL → сразу DEL product:{id} (инвалидация), а не обновление кэша — так проще избежать рассинхронизации при параллельных записях.

CACHE STAMPEDE

Если TTL истёк у популярного ключа и одновременно пришло 500 запросов — все 500 промахнутся мимо кэша и одновременно ударят в PostgreSQL. В лабе (шаг 1.5) решаем через короткий distributed lock на перестройку кэша: первый запрос берёт лок и считает, остальные ждут и читают уже готовое значение или отдают чуть устаревшее.

5.2. Distributed lock

Базовый примитив — SET key value NX PX 5000: ключ создаётся, только если его не было (NX), и автоматически исчезнет через 5 секунд (PX), даже если процесс, взявший лок, упал. Освобождать лок нужно Lua-скриптом, а не голым DEL — иначе можно случайно удалить чужой лок, взятый после того, как ваш истёк по TTL.

-- release_lock.lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
ПОЧЕМУ НЕ ПРОСТО DEL

Сценарий гонки: процесс A берёт лок на 5 сек, зависает на GC-паузе 6 секунд, TTL истекает, лок берёт процесс B. Процесс A просыпается и делает DEL lock:stock:42 — удаляет лок процесса B, который ещё работает. Проверка значения (уникального токена) перед удалением закрывает эту гонку.

5.3. Rate limiting: sliding window log через ZSet

Для лимита «не больше 5 заказов в минуту с одного аккаунта» держим ZSet ratelimit:orders:{user_id}, где score = timestamp в миллисекундах. На каждый запрос: ZREMRANGEBYSCORE удаляет записи старше минуты, ZCARD считает оставшиеся, если меньше лимита — ZADD текущий timestamp. Все три команды — в одном Lua-скрипте, иначе между ZCARD и ZADD может проскочить гонка и лимит будет «мягким».

5.4. Сессии в Redis

SESSION_DRIVER=redis в .env — Laravel сам сериализует сессию в hash/string с TTL. Смысл в лабе — не «показать конфиг», а увидеть последствие: если Redis перезапустится без персистентности, все пользователи разлогинятся одновременно. Это ещё один повод для AOF из раздела 2.3.

6. Redis Streams и consumer groups #

6.1. Stream как append-only лог

Stream4 — упорядоченный, неизменяемый лог записей, каждая с уникальным ID вида 1694000000000-0 (timestamp-sequence). В отличие от очереди RabbitMQ, запись из Stream не удаляется при чтении — она остаётся, пока её явно не обрежут (XTRIM) или не истечёт лимит длины. Это позволяет нескольким независимым consumer group читать один и тот же поток с начала — как analytics.queue и email.queue в RabbitMQ-лабе, только без дублирования события в отдельные очереди на уровне брокера.

6.2. Consumer group, PEL и at-least-once

Consumer group5 (XGROUP CREATE) — именованный «читатель» потока, который помнит, до какого ID он дочитал, и распределяет новые записи между несколькими воркерами внутри группы (competing consumers). Когда воркер забирает запись через XREADGROUP, она попадает в PEL6 (Pending Entries List) — список «выдано, но не подтверждено», ровно как unacked-список канала в RabbitMQ. Подтверждение — XACK, убирает запись из PEL.

RabbitMQRedis Streams
basic.consumeXREADGROUP GROUP ... CONSUMER ...
basic.ackXACK
unacked list каналаPEL группы
redelivery при обрыве каналатребует ручного XCLAIM/XAUTOCLAIM — авто-redelivery нет
prefetchCOUNT в XREADGROUP
delivery_tagStream ID записи
КЛЮЧЕВОЕ ОТЛИЧИЕ

В RabbitMQ обрыв соединения воркера автоматически возвращает unacked-сообщения в очередь. В Redis Streams — нет: запись просто зависает в PEL навечно, пока кто-то явно не вызовет XCLAIM (забрать конкретную запись себе) или XAUTOCLAIM (забрать все зависшие дольше idle-time). Это разбираем на практике в разделе 8 и на шаге 3.1 — самая частая ошибка новичков с Streams: «сообщения теряются», хотя на деле они просто вечно висят непрочитанными в PEL.

6.3. Идемпотентность — тот же принцип, что в RabbitMQ

At-least-once доставка означает, что одна запись может быть обработана дважды (после XCLAIM). Решение то же самое, что в RabbitMQ-лабе: таблица processed_messages с уникальным индексом (stream_id, consumer_group), и маркер пишется в той же транзакции PostgreSQL, что и бизнес-эффект.

7. Сценарий #

Пользователь оформляет заказ: POST /api/orders {user_id, items:[{product_id, qty}]}.

  1. Проверка rate limit по user_id (раздел 5.3) — если превышен, 429.
  2. Lua-скрипт атомарно проверяет и резервирует остаток по каждому товару в Redis (раздел 5.2) — если стока нет, 409 и откат уже зарезервированных позиций.
  3. В одной транзакции PostgreSQL создаются orders + order_items, статус reserved.
  4. XADD orders:stream * с телом заказа и message_id = ID самой записи потока.
  5. Воркеры email-cg (competing consumers, 3 инстанса) шлют письмо через Mailpit; воркер analytics-cg независимо считает метрики.
  6. Каждый обработчик пишет маркер в processed_messages и XACK.
  7. VIP-заказы (priority=high) дополнительно кладутся в ZSet orders:priority и разбираются отдельным воркером вне очереди — раздел 9.
  8. Каждое событие параллельно публикуется в PUBLISH dashboard:orders для live-обновления админ-дашборда.

8. Retry / PEL / ручной DLQ #

В RabbitMQ retry строился на TTL-очередях и DLX. В Redis Streams нет TTL на уровне записи и нет DLX — всё делается явно одним воркером-«надзирателем»:

// упрощённый псевдокод воркера-надзирателя
$claimed = $redis->xautoclaim('orders:stream', 'email-cg', 'reaper', $minIdleMs = 30000, '0');

foreach ($claimed['entries'] as $id => $entry) {
    $attempts = $redis->hIncrBy("retry:attempts:{$id}", 'count', 1);

    if ($attempts > 3) {
        $redis->xAdd('orders:dlq:stream', '*', $entry);
        $redis->xAck('orders:stream', 'email-cg', $id);
        $redis->del("retry:attempts:{$id}");
    }
    // иначе запись просто снова взята консьюмером reaper и уйдёт на переобработку
    // при следующем цикле XREADGROUP того же consumer'а
}
Зачем именно так: XAUTOCLAIM с min-idle-time=30000 means «забери все записи, которые провисели неподтверждёнными больше 30 секунд» — это и есть аналог visibility timeout из SQS/RabbitMQ-DLX. Счётчик попыток живёт отдельным Hash-ключом, потому что сама запись Stream неизменяема — в неё нельзя дописать x-death, как это делает RabbitMQ автоматически.
🔬 Под капотом: почему multi-step retry с TTL-очередями (как в RabbitMQ) на Streams не построить так же

В RabbitMQ-лабе задержка между попытками делалась через каскад TTL-очередей (10с → 30с → 300с) с DLX-возвратом в основную очередь. У Stream нет TTL на отдельную запись и нет DLX-редиректа — единственный способ «отложить» переобработку — либо polling-надзиратель с растущим min-idle-time, либо отдельная ZSet-очередь «отложенных» ID с score=время следующей попытки, которую worker периодически вычитывает через ZRANGEBYSCORE ... WITHSCORES LIMIT и возвращает готовые обратно в обработку. В лабе используем первый, более простой вариант — второй упомянут в разделе 15 как усложнение для самостоятельной практики.

9. Priority, competing consumers, Pub/Sub #

9.1. Competing consumers и COUNT

Несколько инстансов воркера с одним и тем же GROUP, но разным CONSUMER-именем автоматически делят поток новых записей между собой — Redis сам не отдаст одну и ту же новую запись двум консьюмерам группы. COUNT в XREADGROUP — прямой аналог prefetch_count: сколько записей забрать за один вызов.

9.2. Приоритет через ZSet, а не через Stream

У Streams нет встроенного приоритета (в отличие от x-max-priority в RabbitMQ). VIP-заказы кладутся отдельно в ZSet orders:priority с score = приоритет, и отдельный воркер вычитывает их через ZPOPMIN/BZPOPMIN вне очереди обычного потока — то есть приоритет реализован архитектурно (отдельный канал), а не встроенным свойством одной очереди.

9.3. Pub/Sub — fanout без памяти

PUBLISH/SUBSCRIBE рассылает сообщение всем текущим подписчикам мгновенно — похоже на fanout-exchange из RabbitMQ. Критическое отличие: если подписчика не было в момент публикации — сообщение потеряно навсегда, Redis его нигде не хранит. Fanout-очередь RabbitMQ, наоборот, копит сообщения, пока их не заберёт живой consumer.

ПОЧЕМУ ЭТО ОК ДЛЯ ДАШБОРДА И НЕ ОК ДЛЯ ЗАКАЗОВ

Live-дашборд admin-панели теряет значение, если событие устарело на минуту — поэтому Pub/Sub здесь уместен. Для самого заказа мы используем Stream (персистентный, с PEL), а Pub/Sub — только «уведомление о том, что что-то произошло», без гарантий доставки. Смешивать эти две роли — частая ошибка.

9.4. Что не решает ни один из примитивов Redis сам по себе

Ни Stream, ни Pub/Sub не дают routing по паттерну ключа, как topic-exchange в RabbitMQ (order.*). Если нужна такая маршрутизация — её либо эмулируют неймингом отдельных Stream'ов на каждый тип события, либо фильтруют на стороне consumer'а после чтения общего потока. В лабе — один общий orders:stream, и фильтрация по полю event_type внутри воркера.

Шаг 1.5Cache-Aside — app/Services/ProductCache.php#
<?php
namespace App\Services;

use App\Models\Product;
use Illuminate\Support\Facades\Redis;

final class ProductCache
{
    private int $ttl = 60; // секунд

    public function get(int $id): ?array
    {
        $cached = Redis::get("product:{$id}");
        if ($cached !== null) {
            return json_decode($cached, true);
        }

        // защита от cache stampede: только один процесс идёт в БД
        $lockKey = "lock:product-rebuild:{$id}";
        $token = uniqid('', true);
        $gotLock = Redis::set($lockKey, $token, 'PX', 3000, 'NX');

        if (!$gotLock) {
            usleep(100_000);
            return $this->get($id); // короткая рекурсия, пока другой процесс строит кэш
        }

        $product = Product::find($id);
        $payload = $product ? $product->only(['id', 'name', 'stock']) : null;
        Redis::setex("product:{$id}", $this->ttl, json_encode($payload));
        $this->releaseLock($lockKey, $token);

        return $payload;
    }

    public function invalidate(int $id): void
    {
        Redis::del("product:{$id}");
    }

    private function releaseLock(string $key, string $token): void
    {
        Redis::eval(
            'if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) else return 0 end',
            1, $key, $token
        );
    }
}
Зачем: это раздел 5.1 и 5.2 в коде: cache-aside плюс тот самый лок с токеном из release_lock.lua, только через Redis::eval вместо отдельного файла — для одной строки скрипта так проще.
🔬 Под капотом: почему рекурсия в get(), а не цикл

Рекурсия здесь безопасна: глубина ограничена временем жизни лока (3 секунды) и коротким usleep, на практике 1-3 повторных вызова. В продакшене вместо самодельного повтора обычно ставят экспоненциальный backoff с максимальным числом попыток и таймаутом — иначе при затянувшемся построении кэша (например, БД легла) стек вызовов может расти неограниченно.

Шаг 1.7StreamPublisher и OrderController#
<?php
namespace App\Services;

use Illuminate\Support\Facades\Redis;

final class StreamPublisher
{
    public function publishOrderCreated(int $orderId, array $payload): string
    {
        $fields = array_merge($payload, [
            'event' => 'order.created',
            'order_id' => (string) $orderId,
            'occurred_at' => now()->toIso8601String(),
        ]);
        // XADD orders:stream * field1 value1 field2 value2 ...
        return Redis::xAdd('orders:stream', '*', $fields);
    }
}
// app/Http/Controllers/OrderController.php (упрощённо)
public function store(Request $request, StreamPublisher $publisher)
{
    $order = DB::transaction(function () use ($request) {
        $order = Order::create(['user_id' => $request->user_id, 'status' => 'reserved']);
        foreach ($request->items as $item) {
            OrderItem::create(['order_id' => $order->id, ...$item]);
        }
        return $order;
    });

    $streamId = $publisher->publishOrderCreated($order->id, ['user_id' => $order->user_id]);

    return response()->json(['order_id' => $order->id, 'stream_id' => $streamId], 201);
}
Зачем: Redis::xAdd(..., '*', ...) — звёздочка означает «пусть Redis сам сгенерирует ID» (timestamp-sequence), это и есть наш будущий message_id. Публикация — после коммита в PostgreSQL, а не до: если commit упадёт, лишнего события в Stream не будет.
🔬 Под капотом: почему это не outbox pattern, и когда его всё же придётся добавить

В RabbitMQ-лабе между записью в БД и публикацией стоял Outbox Pattern — отдельная таблица и relay-процесс, потому что «записать в БД» и «опубликовать в брокер» это две разные системы, и без Outbox между ними возможна потеря события при падении между двумя шагами. Здесь тот же риск: если процесс упадёт между строкой с DB::transaction и xAdd, PostgreSQL будет знать о заказе, а Stream — нет. Лаба сознательно не усложняет это Outbox'ом, чтобы держать фокус на Streams, но в проде для Redis тот же паттерн строится один в один: таблица outbox_messages + relay-воркер, который читает её и делает XADD.

Шаг 1.8Первый consumer — happy path#
php artisan make:command EmailWorker
<?php
namespace App\Console\Commands;

use Illuminate\Console\Command;
use Illuminate\Support\Facades\Redis;
use App\Models\ProcessedMessage;
use Illuminate\Support\Facades\DB;

class EmailWorker extends Command
{
    protected $signature = 'worker:email {consumer}';

    public function handle(): void
    {
        $stream = 'orders:stream';
        $group  = 'email-cg';
        $consumer = $this->argument('consumer');

        try {
            Redis::xGroup('CREATE', $stream, $group, '0', true);
        } catch (\Throwable $e) { /* группа уже существует — ок */ }

        $this->info("email worker [{$consumer}] запущен");

        while (true) {
            $messages = Redis::xReadGroup($group, $consumer, [$stream => '>'], 5, 5000);
            if (empty($messages[$stream])) { continue; }

            foreach ($messages[$stream] as $id => $fields) {
                $this->process($id, $fields, $group);
            }
        }
    }

    private function process(string $id, array $fields, string $group): void
    {
        $already = ProcessedMessage::where('stream_id', $id)->where('consumer_group', $group)->exists();
        if (!$already) {
            DB::transaction(function () use ($id, $fields, $group) {
                // здесь реальная отправка письма через Mail::...
                ProcessedMessage::create([
                    'stream_id' => $id, 'consumer_group' => $group, 'processed_at' => now(),
                ]);
            });
        }
        Redis::xAck('orders:stream', $group, $id);
    }
}
Зачем: XGROUP CREATE ... '0' с флагом MKSTREAM создаёт группу, начиная читать с самого начала потока ('0'), а не только новые записи — это выбор для лабы, чтобы ничего не терять при первом запуске. '>' в xReadGroup означает «только новые, ещё не выданные этой группе записи», а не перечитывание PEL.

Шаг 2.1Атомарный Lua-скрипт — StockReservationService#
<?php
namespace App\Services;

use Illuminate\Support\Facades\Redis;

final class StockReservationService
{
    private const RESERVE_LUA = <<<'LUA'
        local stock = redis.call('GET', KEYS[1])
        if stock == false then return -1 end
        if tonumber(stock) < tonumber(ARGV[1]) then return 0 end
        redis.call('DECRBY', KEYS[1], ARGV[1])
        return 1
    LUA;

    public function reserve(int $productId, int $qty): bool
    {
        $key = "stock:{$productId}";
        $result = Redis::eval(self::RESERVE_LUA, 1, $key, $qty);
        return $result === 1;
    }

    public function release(int $productId, int $qty): void
    {
        Redis::incrby("stock:{$productId}", $qty);
    }
}
Зачем: проверка и списание — одна атомарная Lua-операция (раздел 2.5), а не «GET, сравнить в PHP, DECRBY» тремя отдельными вызовами, между которыми Redis успел бы обслужить другого клиента.
🔬 Под капотом: откуда берётся ключ stock:{id}, и почему не читаем прямо из PostgreSQL

stock:{id} — отдельный «горячий» счётчик в Redis, синхронизируемый с колонкой products.stock отдельным заданием (например, при старте контейнера — SET stock:{id} {значение из БД}). Идея та же, что с priority-очередью в RabbitMQ-лабе: то, что должно решаться очень быстро и под конкурентной нагрузкой, выносится в Redis, а PostgreSQL остаётся источником истины для отчётности и восстановления после сбоя. В проде за синхронизацию этих двух чисел отвечает отдельный процесс сверки (reconciliation job) — за рамками лабы, но упомянут в разделе 15.

Шаг 2.2Rate limiter (sliding window)#
<?php
namespace App\Services;

use Illuminate\Support\Facades\Redis;

final class SlidingWindowRateLimiter
{
    private const LUA = <<<'LUA'
        local key = KEYS[1]
        local now = tonumber(ARGV[1])
        local window = tonumber(ARGV[2])
        local limit = tonumber(ARGV[3])

        redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
        local count = redis.call('ZCARD', key)
        if count >= limit then return 0 end
        redis.call('ZADD', key, now, now .. '-' .. math.random())
        redis.call('PEXPIRE', key, window)
        return 1
    LUA;

    public function allow(int $userId, int $limit = 5, int $windowMs = 60000): bool
    {
        $now = (int) (microtime(true) * 1000);
        $result = Redis::eval(self::LUA, 1, "ratelimit:orders:{$userId}", $now, $windowMs, $limit);
        return $result === 1;
    }
}
Зачем: это раздел 5.3 целиком в одном атомарном скрипте — без Lua между ZCARD и ZADD два одновременных запроса могли бы оба пройти проверку и оба добавить себя, временно превысив лимит.

СЕССИЯ 3 — Retry, DLQ, приоритет, Pub/Sub ~3 часа
Шаг 3.1Retry через XAUTOCLAIM#
php artisan make:command StreamReaper
<?php
namespace App\Console\Commands;

use Illuminate\Console\Command;
use Illuminate\Support\Facades\Redis;

class StreamReaper extends Command
{
    protected $signature = 'worker:reaper';
    private int $maxAttempts = 3;

    public function handle(): void
    {
        $stream = 'orders:stream';
        $group  = 'email-cg';
        $minIdleMs = 30000;
        $cursor = '0';

        while (true) {
            [$cursor, $claimed] = Redis::xAutoClaim($stream, $group, 'reaper', $minIdleMs, $cursor, 10);

            foreach ($claimed as $id => $fields) {
                $attempts = Redis::hIncrBy("retry:attempts:{$id}", 'count', 1);

                if ($attempts > $this->maxAttempts) {
                    Redis::xAdd('orders:dlq:stream', '*', $fields + ['original_id' => $id, 'attempts' => $attempts]);
                    Redis::xAck($stream, $group, $id);
                    Redis::del("retry:attempts:{$id}");
                    $this->warn("id={$id} ушёл в DLQ после {$attempts} попыток");
                } else {
                    $this->info("id={$id} попытка {$attempts}/{$this->maxAttempts} — вернулся в обработку");
                }
            }
            sleep(5);
        }
    }
}
Зачем: это раздел 8 в коде. XAUTOCLAIM с курсором позволяет проходить по всему PEL пачками по 10, не блокируя Redis долгим циклом — прямой аналог постраничного сканирования.
🔬 Под капотом: почему после XAUTOCLAIM запись не сразу ушла — она же теперь у "reaper"

После XAUTOCLAIM запись формально принадлежит consumer'у reaper, но остаётся в PEL — она не считается «обработанной» до явного XACK. В коде выше мы не ackаем её при повторной попытке — вместо этого следующий вызов xReadGroup живого email-воркера её не получит (она не новая), но следующий цикл reaper'а через 30 секунд снова заберёт её себе через XAUTOCLAIM, увеличит счётчик и т.д. Чтобы запись реально ушла обратно живому воркеру, reaper должен передать её ему явным XCLAIM на нужного consumer'а — в проде это делают перезапуском consumer-имени по round-robin. В лабе для простоты reaper сам исполняет retry-логику вместо передачи записи дальше.

12. Полный чек-лист концепций #

  • Однопоточность Redis и почему KEYS опасен в проде.
  • Cache-Aside: read-through на промахе, invalidate-on-write, защита от cache stampede локом.
  • Distributed lock: SET NX PX, обязательная проверка токена перед DEL.
  • Атомарность составной операции через Lua (EVAL) — резервирование стока, rate limiter.
  • Sliding window rate limiting на ZSet: ZREMRANGEBYSCORE + ZCARD + ZADD.
  • Redis Streams: XADD, ID записи, неизменяемость и множественное независимое чтение.
  • Consumer groups: XGROUP CREATE, XREADGROUP, PEL, XACK.
  • Отсутствие авто-redelivery в Streams — необходимость XCLAIM/XAUTOCLAIM.
  • Ручной retry-счётчик (Hash) и ручной DLQ (отдельный Stream) — сравнение с DLX/DLQ RabbitMQ.
  • Приоритет через отдельный ZSet + BZPOPMIN, а не встроенное свойство очереди.
  • Pub/Sub как fanout без персистентности — когда это ок, а когда нет.
  • Идемпотентность: маркер в той же транзакции, что и эффект, уникальный индекс по (stream_id, consumer_group).
  • Персистентность: RDB vs AOF, appendfsync, что теряется при разных настройках.
  • Eviction policies и почему volatile-lru безопаснее allkeys-lru для смешанной нагрузки.

13. Глоссарий терминов #

1. Однопоточность (single-threaded) ↩ — вся логика команд Redis выполняется одним потоком через event loop; убирает внутренние гонки, но делает каждую медленную команду блокирующей для всех клиентов.

2. Персистентность ↩ — сохранение данных Redis на диск через RDB (снапшоты) и/или AOF (журнал команд), чтобы пережить рестарт процесса.

3. TTL (Time To Live) ↩ — время жизни ключа, после которого Redis удаляет его автоматически; задаётся через EX/PX/EXPIRE.

4. Stream ↩ — тип данных Redis: упорядоченный, неизменяемый append-only лог записей с уникальными ID, поддерживающий множественное независимое чтение и consumer groups.

5. Consumer group ↩ — именованный читатель Stream'а, распределяющий новые записи между несколькими consumer'ами и отслеживающий, какие записи уже подтверждены.

6. PEL (Pending Entries List) ↩ — список записей, выданных consumer'у группы, но ещё не подтверждённых через XACK; аналог unacked-списка канала в RabbitMQ.
